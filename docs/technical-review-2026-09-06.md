# WaterMedia technical review

Initial review: September 6, 2026. Implementation review: September 7, 2026. Final LGPL verification: September 16, 2026. Scope: lifecycle, media/network contracts, documentation, tests, native provisioning, build reproducibility and selected published dependency advisories. This is a targeted review, not a security certification or a complete native dependency audit.

The original recommendations were followed by an implementation pass. The ledger below separates implemented changes, measured behavior and work that still requires external validation. P1 denotes a security or significant correctness concern, P2 a functional/regression concern, and P3 maintenance or diagnostics. Java paths may omit the common `src/main/java/org/watermedia/` or `src/test/java/org/watermedia/` prefix; `binaries/...` identifies the separate binaries module. Method names identify the inspected contracts when surrounding line numbers change.

## Spatial audio

The new API exposes mono spatial playback through `SFXEngine.SpatialAudio` and an environment callback implemented by a host adapter. The supplied root Sound Physics artifact is a source ZIP, despite being described as a jar in the request. Its actual source was inspected to establish OpenAL source/context ownership, EFX sends, position updates, category filtering and configuration gates. The integration contract, compiled example and defaults are documented in [SPATIAL_AUDIO.md](SPATIAL_AUDIO.md).

Tests exercise real OpenAL mono negotiation, stereo-to-mono FFmpeg conversion, moving source state, callback/reset failures, context mismatch, release and late-update rejection. Minecraft world access, listener updates and Sound Physics callbacks must run on the host's serialized context/thread. `auxOnly` is an adapter request: if the adapter is disabled or does nothing, the host must mute when strict silence is required. A real Minecraft/Sound Physics smoke test has not run on this machine.

## Native HTTPS verification

The original FFmpeg 8.1.2 source defines `TLS_VERIFY_DEFAULT` as zero while libavformat major is below 63. Its OpenSSL backend enables peer-chain verification only when that option is enabled. Even with explicit verification, the `tls_open` numeric-host condition skips `SSL_set1_host`, allowing a trusted certificate for a different identity to serve an IP URL. These are source-level transport defects demonstrated locally, not newly assigned CVEs. [Pinned FFmpeg TLS options](https://github.com/FFmpeg/FFmpeg/blob/n8.1.2/libavformat/tls.h), [OpenSSL transport](https://github.com/FFmpeg/FFmpeg/blob/n8.1.2/libavformat/tls_openssl.c).

Nested requests added another boundary: `ffio_copy_url_options` did not carry TLS settings, and HTTP's private TLS context was not reachable through its public AVOption children. An initial authenticated playlist therefore did not establish authentication for its subsequent HLS playlist, initialization, key or segment requests, or DASH initialization/segment requests. The patch adds retained HTTP options and explicit forwarding, extends the shared copy list and exposes the existing HLS/DASH dictionaries as `protocol_opts`. It validates IP identities through OpenSSL's existing `SSL_set1_host` implementation while retaining SNI only for DNS names. No fixed initial hostname is copied across CDN redirects. [Shared URL options](https://github.com/FFmpeg/FFmpeg/blob/n8.1.2/libavformat/aviobuf.c), [HTTP context](https://github.com/FFmpeg/FFmpeg/blob/n8.1.2/libavformat/http.c).

Java exports a deduplicated PEM from `TrustManagerFactory.init((KeyStore) null)` once per media session and supplies `tls_verify=1`, `ca_file` and the natively escaped `protocol_opts` dictionary to both FFmpeg inputs. Configuration also removes preexisting insecure aliases and `verifyhost`, so caller-supplied options cannot substitute another peer identity. A custom JVM truststore therefore supplies the accepted anchors without changing global host TLS settings. This shares trust anchors; it does not execute arbitrary custom Java trust-manager code or reproduce every JSSE algorithm/revocation policy inside OpenSSL. Session cleanup owns the PEM until player cleanup succeeds. Unpatched natives fail initialization instead of silently providing unauthenticated HTTPS.

`VerifyTLS.java` contains **58 local JNI scenarios**: 29 certificate/transport cases and 29 credential-origin cases. All 58 pass against each of the five final candidates. The transport group covers private trust, DNS/IP identity, unknown chains, redirects, strict defaults, Unicode CA paths, HLS/DASH initialization and later segments, plain-HTTP manifests and local manifests. Each certificate-rejection case checks that the rejected HTTPS endpoint received no HTTP request. Remote manifests receive only flat TLS options so their tests depend on actual HTTP option propagation; local inputs exercise the demuxer dictionary. Local fixtures explicitly authorize their test network protocols; production protocol whitelists remain unchanged. The tool compiles for Java 17. Against the original Maven libraries, the wrong-IP case fails by reading a packet from the wrong peer.

`TLSLifecycleProbe` passed with the final Windows header-isolated candidate loaded into a fresh Java 17 process, recorded in `build/tls-headers-candidate-lifecycle.log`. It ends with `BOOTSTRAP_OK tls` and includes null-argument rejection, `verifyhost` removal and the current `header_origin` capability gate. ## Native credential origins

The previous Windows security candidate still replayed `Authorization`, `Cookie` and `X-WaterMedia-Token` across hostname, port and HTTPS-to-HTTP changes. Twelve completed local JNI cases demonstrate this in redirects, child HLS playlists, initialization requests and media segments; the log is `build/native-header-audit/result.log`. This affects real source metadata: BiliBili can attach the user's configured session cookie, TikTok attaches captured WAF cookies, and yt-dlp copies arbitrary per-format `http_headers`. Twitch's current adapter uses ordinary headers and URL tokens. Java redirect handling does not protect later FFmpeg connections, and the media cache does not cover HLS/DASH streams or every download.

The separate `ffmpeg-headers.patch` has SHA-256 `c7a6f12f22d779733e323d932da697368cc012a07dc7e894729a921a5f7a7cd7`. HTTP records an immutable `header_origin`, which the shared URL-option copier retains for HLS/DASH. Each request compares scheme, hostname and effective port, including default ports. Across an origin boundary it removes `Authorization`, `Proxy-Authorization`, `Cookie`, `Cookie2` and `X-WaterMedia-Token`, regenerates `Host`, and preserves ordinary CDN headers. Filtering recognizes CR, LF and CRLF and normalizes retained lines. Generated cookies obey the same boundary; foreign `Set-Cookie` responses are ignored and cannot replace cookies when a redirect returns to the initial origin. This deliberately provides one credential origin per input, not independent cookie sessions for redirected servers.

The patch removes complete HTTP request/reply and header traces, replaces cookie-value parse warnings with generic diagnostics, and removes the server's raw requested-resource trace. TikTok's Java cookie debug statement was removed separately. This describes those explicit logging paths; it is not a claim that every native or host log redacts every media URL.

Both affected C files compile to objects in isolated scratch, recorded in `build/ffmpeg-headers-patch/compile.log`, and the completed patch is compiled and validated in all five final candidates. Independent C/test review and the full source round trip pass. The 29 credential scenarios require preserved same-origin credentials, stripped cross-origin credentials, correct Host, preserved X-Test and actual hits for every expected redirect, playlist, initialization and segment URL. They cover raw and generated cookies, return-to-origin cookie injection and bare-CR boundaries. The prior candidate fails the first cross-host case after 36 successful checks, as recorded in `build/native-header-audit/verify-before.log`; every final candidate passes all 58 checks.

## Optimization measurement

The duplicated input and binary-download policies were consolidated, and disabled native provisioning is avoided. Decoder loops remain local rather than being fragmented into unnecessary helpers.

A separate observational Java probe decoded `gif/3.gif` (1,038,601 encoded bytes, 564 frames) with one, two and four concurrent readers. Each fresh JVM retained all decoded frames, used a 2 GiB heap/direct-memory ceiling and sampled `BufferPoolMXBean` every 5 ms. Measurements on this Windows host were:

| Readers | Retained frame bytes | Peak direct-memory delta | Peak heap delta | Elapsed |
| --- | ---: | ---: | ---: | ---: |
| 1 | 216,576,000 | 216,960,000 | 14,680,064 | 972 ms |
| 2 | 433,152,000 | 433,920,000 | 15,728,640 | 995 ms |
| 4 | 866,304,000 | 867,840,000 | 15,728,640 | 1,270 ms |

The measurement confirms that the per-read 512 MiB limit does not bound aggregate process memory. It is a `readAll` retention experiment, not a prediction for streaming players, which have separate prefetch/VRAM budgets. No arbitrary global memory cap was introduced without a workload/admission policy. The local measurement output is `build/reports/concurrent-image-memory.tsv`; the large experiment is deliberately outside routine CI.
